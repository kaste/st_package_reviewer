# Linter rules and messages

This document is the catalog of reports emitted by `st_package_reviewer`. It is
both an end-user reference and a specification of the reviewer's current
message text.

The rules are grouped by topic rather than by source module. Future rationale
and resolution guidance should live with the relevant rule.

## How to read this document

### Severities

Every rule report has one of three severities:

- **Failure**: the package does not pass review.
- **Warning**: the package may have a problem or should follow a recommended
  convention.
- **Notice**: informational advice or a successful status report.

`--fail-on-warnings` makes warnings affect the process exit status, but does not
change their displayed severity.
### Message notation

Text in angle brackets, such as `<package name>`, is substituted at runtime.
Literal quotes, backticks, capitalization, and punctuation shown in message
blocks are part of the emitted message. A block containing several bullets
lists every textual variant of that message.

Some reports are followed by context lines. These are not part of the message:

```
    File: <relative path>
    Binding: <JSON object>
    Line: <line number>
    Line: <line number>, Column: <column number>
    Exception: <exception text>
```

A top-level filename may be omitted from the context when the message itself
starts with that quoted filename. The renderer prefixes messages with `- ` and
context lines with four spaces.

The report renderer also emits group headings with singular and plural forms:

```
Reporting 1 failure:
Reporting <N> failures:
Reporting 1 warning:
Reporting <N> warnings:
No failures
No warnings
No failures, no warnings. 👍
```

With `--compact`, `Reporting ` is omitted from non-empty group headings.
Headings and repository introductions are presentation text, not linter rules.

singular form.

**Severity:** Failure
**Source:** `st_package_reviewer/check/file/check_resource_files.py` —
`CheckPluginsInRoot.check`




### Root package initializer contains code

```
The root-level '__init__.py' must be empty or contain only comments. Package Control discards this file during installation to avoid Sublime Text reload errors, so it cannot be used as the entrypoint for your package. You may also want to remove it if it is not needed by your development tooling.
```

A root `__init__.py` may be kept as an empty or comment-only tooling marker. It
is not treated as an installed plugin or resource. Initializers in subpackages
are unaffected.

**Severity:** Failure
**Source:** `st_package_reviewer/check/file/check_redundant_files.py` —
`CheckRootInitContents.check`

```
* The binding <keys> has no context. Packages should only ship key bindings that use a specific context such as 'selector', 'setting.*', or a custom context key. If the binding defines a main entry-point to your package, move it to an example keymap instead so users can decide on their own.

The plural variants are:

```
* Multiple bindings, e.g. <first keys> and <second keys>, have no context. Packages should only ship key bindings that use a specific context such as 'selector', 'setting.*', or a custom context key.
